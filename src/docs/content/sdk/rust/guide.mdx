# Build With Rust

Use the Rust SDK in Tauri backends and native Rust desktop apps. It owns the
complete native mode model: direct for lowest latency, broker for helper-process
isolation, and server when independent PostgreSQL clients are required.

Execution placement is a separate choice. The root API is synchronous and runs
PostgreSQL or protocol transport on the calling thread. The explicit
`oliphaunt::worker` API owns a dedicated thread and exposes the same concepts
through async methods.

<Callout type="info" title="Rust owns the complete native mode surface">
Use this guide when the app runtime is Rust. Tauri webviews and desktop
JavaScript apps use their SDKs and call into Rust through app commands or helper
processes.
</Callout>

<SdkGuideSummary id="rust" />

<Steps>
<Step>

### Install

Add the crate and let the SDK resolve released runtime assets and helpers
through configuration:

```toml
[dependencies]
oliphaunt = "0.1"
```

</Step>
<Step>

### Open and query

Create a builder, choose storage, select exact extensions, open, query, and
close.

<!-- oliphaunt-snippet: oliphaunt-rust -->

```rust
use oliphaunt::{Extension, Oliphaunt};

fn open_database() -> oliphaunt::Result<()> {
    let mut db = Oliphaunt::builder()
        .directory(".oliphaunt")
        .direct()
        .extension(Extension::Vector)
        .open()?;

    let rows = db.query("SELECT 1::text AS value")?;
    let value: &str = rows.rows()[0].try_get("value")?;
    assert_eq!(value, "1");

    db.close()?;
    Ok(())
}
```

The root handle is exclusive, `!Send + !Sync`, and stays on the thread that
opened it. Keep it in thread-local application state or on an application-owned
database thread. Use `oliphaunt::worker::Oliphaunt` when async tasks need a
cloneable `Send + Sync` handle. Cloned worker handles point to the same owner and
do not create additional PostgreSQL sessions.

</Step>
<Step>

### Create app data

Use typed helpers for application queries:

```rust
db.execute(
    r#"
    CREATE TABLE IF NOT EXISTS notes (
        id bigserial PRIMARY KEY,
        title text NOT NULL,
        body text NOT NULL,
        created_at timestamptz NOT NULL DEFAULT now()
    )
    "#,
)?;

db.query_with_params(
    "INSERT INTO notes (title, body) VALUES ($1, $2) RETURNING id::text AS id",
    ["First note", "Stored by embedded PostgreSQL"],
)?;

let notes = db.query("SELECT id, title FROM notes ORDER BY id DESC LIMIT 20")?;
let first_title: String = notes.rows()[0].try_get("title")?;
```

Expose app-specific commands to a Tauri webview instead of exposing raw database
handles directly to frontend code.

</Step>
<Step>

### Configure

Configure storage, runtime selection, startup identity, PostgreSQL startup GUCs,
selected extensions, broker executable, and server executable through the
builder. `Oliphaunt::builder()` defaults to an SDK-owned temporary directory
initialized from the packaged cluster seed; call `.directory(path)` when data must
persist.

The terminal validates topology-specific choices. Use `broker_executable` only
with `broker().open()`, and use `listen` or `server_executable` only with
`open_server()`. Do not add `.direct()` or `.broker()` before `open_server()`;
mismatches return `InvalidConfig` rather than being ignored.

</Step>
<Step>

### Choose execution placement

Use the root import when the current thread is intentionally the database
thread:

```rust
use oliphaunt::Oliphaunt;

let mut db = Oliphaunt::builder().temporary_directory().open()?;
let rows = db.query("SELECT 42::text AS answer")?;
```

Use the explicit worker import when the application executor must stay free:

```rust
use oliphaunt::worker::Oliphaunt;

let db = Oliphaunt::builder().temporary_directory().open().await?;
let rows = db.query("SELECT 42::text AS answer").await?;
```

The worker runs PostgreSQL synchronously on its own thread. Async calls cross a
bounded in-process queue and resolve when that worker replies; they do not make
one PostgreSQL session execute queries concurrently.

</Step>
<Step>

### Choose a mode

`direct()` runs one serialized embedded session in the process. With the root
API it is a no-hop call; with `oliphaunt::worker` it runs on the owner thread.

`broker()` talks to a local helper process. Use it for desktop apps that need
process isolation, crash recovery, or several instances managed by one application.

`open_server()` starts a PostgreSQL-compatible server process and returns an
`OliphauntServer`. Use its connection string when `psql`, ORMs, or true
independent client sessions matter.

</Step>
<Step>

### Handle lifecycle

Root transactions exclusively borrow the database until commit or rollback,
and `close()` tears down synchronously. Before starting a long root call, obtain
`db.cancel_handle()` and move that small thread-safe capability to the thread
which may interrupt it.

Worker work queues fairly on one owner executor. Worker `close().await`
establishes an ordered cutoff: work already admitted drains, later application
work is rejected, and then the selected runtime closes or detaches. A required
`COMMIT` or `ROLLBACK` remains admissible for a transaction whose `BEGIN`
crossed the cutoff first. Worker `cancel().await` is out of band and does not
wait behind the SQL FIFO.

Once either placement starts runtime teardown, the handle is terminal even
when teardown fails: `is_closed()` is true, later work is rejected, and
repeated close calls return the same retained result.

</Step>
<Step>

### Select extensions

Select exact SQL extension names before open. There are no packs, aliases, or
implicit selectors. If you select `vector`, the generated artifacts include
`vector` and only its declared dependencies.

</Step>
<Step>

### Back up and restore

Use `backup()` and static restore instead of copying PostgreSQL directories from
application code. Direct and broker expose the one native physical archive;
restore accepts a new or existing-empty destination. Root backup and restore
are synchronous. Their `oliphaunt::worker` counterparts are async and move
blocking work off the polling executor thread. Server applications use normal
PostgreSQL tooling.

</Step>
<Step>

### Use logical tools

Add the separate `oliphaunt-tools` crate when a server application needs plain
`pg_dump` or non-interactive `psql`. Pass `server.connection_string()` to the
tool; the core `oliphaunt` crate does not install or depend on client programs.

```rust
use oliphaunt_tools::{PgDumpOptions, pg_dump};

let sql = pg_dump(
    server.connection_string(),
    PgDumpOptions::new().arg("--schema-only"),
)?;
```

</Step>
</Steps>

## Troubleshooting

Check storage ownership errors, missing runtime assets, unsupported-mode errors, extension
selection errors, and SQLSTATE-bearing PostgreSQL errors. If concurrency looks
surprising, confirm the selected mode first: direct mode serializes work by
design, while independent sessions require server mode. If the issue is a
blocked async executor rather than database placement, confirm the import:
`oliphaunt::Oliphaunt` is caller-thread synchronous and
`oliphaunt::worker::Oliphaunt` owns a dedicated thread.
