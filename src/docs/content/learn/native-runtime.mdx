---
title: Choose how PostgreSQL runs
description: Compare native PostgreSQL modes and WebAssembly execution placement for your application.
---

Choose the PostgreSQL runtime through your [SDK package](/docs/sdk), then choose where its work runs. Native Rust and native TypeScript offer the three modes below. Swift, Kotlin, and React Native use direct or mobile broker integration. The [WASIX execution choices](#webassembly-execution) are separate from these native PostgreSQL modes.

| Mode | Database runs in | Access | Choose it when |
| --- | --- | --- | --- |
| Direct | Your application process | SDK query handle, one session | You want embedded queries with the fewest moving parts |
| Broker | A helper process | SDK query handle, one session | You need to isolate database execution from your app process |
| Server | A server process | PostgreSQL connection string | You need a driver, ORM, pool, or independent sessions |

## Direct

For native PostgreSQL SDKs, direct mode is the default. The SDK manages a resident native backend in the application process. Keep one application-owned database handle and share it according to your language's concurrency rules.

The first successful direct open binds the process to that root and configuration. Closing the handle releases the logical session; it does not unload PostgreSQL or let the process switch roots. Reopen the same root with compatible settings, or use broker/server mode for multiple roots. In direct mode, mobile apps switch to restored data on a subsequent process launch.

In Rust, the synchronous handle blocks the calling thread. Use `AsyncOliphaunt` for async tasks. Swift, Kotlin, and JavaScript expose async APIs; those APIs serialize database work rather than creating a session per call.

## Broker

Broker mode moves execution into a helper process while retaining the SDK query API. It is available in native Rust and desktop TypeScript, and through platform-specific setup on iOS 26+ and Android. See [mobile broker setup](/docs/learn/mobile-stability#broker-mode).

If the helper exits unexpectedly, the database handle becomes unusable. Close it and open a new handle on the same persistent directory. PostgreSQL recovers committed data from WAL. The SDK does not replay a failed operation, because its commit outcome may be unknown.

Package the helper executable and runtime resources with your app. Use the package's normal resource resolution unless your deployment layout requires an explicit path.

## Server

Server mode returns a lifecycle handle with a PostgreSQL connection string. Connect with a PostgreSQL driver or ORM to run queries; the server handle itself does not provide the embedded query API.

Keep the server handle alive for as long as clients use it. At shutdown, stop accepting application work, close client connections and pools, then close the server. A copied connection string does not keep the server running.

See [Rust runtime recipes](/docs/sdk/rust/guide#choose-a-runtime-mode) or [TypeScript runtime recipes](/docs/sdk/typescript/guide#choose-a-runtime-mode). For a desktop webview, see [Use with Tauri](/docs/learn/tauri).

## WebAssembly execution

The [WASIX SDKs](/docs/sdk#postgresql-as-webassembly) run the WebAssembly PostgreSQL runtime in your host application. These choices control scheduling; every embedded handle still owns one session.

| Host | Default execution | Use for responsive application work |
| --- | --- | --- |
| Browser TypeScript | Importing realm; can block its thread | `/worker` in a package-owned module Worker |
| Node.js, Bun, Deno, Electron | Dedicated Rust owner thread | Root import, or `/worker` for a JavaScript Worker |
| Rust desktop and Tauri | Synchronous calling thread | `AsyncOliphaunt` on a dedicated owner thread |

Desktop TypeScript also exposes `/direct` for caller-thread execution. A promise does not guarantee that a query runs off the calling thread. See [TypeScript placement](/docs/sdk/wasix-typescript/guide#choose-execution-placement) and [Rust ownership](/docs/sdk/wasix-rust/runtime#thread-ownership).

Native PostgreSQL's process-wide direct-root binding does not describe WASIX handles. WASIX persistent storage still allows only one live owner per root or browser storage name.

## WASIX endpoints

WASIX SDKs provide a local PostgreSQL endpoint on supported desktop hosts. It serves one connected client at a time; configure a pool with a maximum of one connection. Keep the server handle alive and close clients before shutting it down. Browser apps cannot open this TCP listener.

Use [WASIX Rust endpoints](/docs/sdk/wasix-rust/runtime#local-postgresql-endpoint) or [WASIX TypeScript `/server`](/docs/sdk/wasix-typescript/guide#open-a-local-endpoint) when a driver expects a PostgreSQL URL. For independent client sessions, use native server mode above.

The separate [WASIX postmaster product](https://github.com/f0rr0/oliphaunt/tree/main/src/wasix/postmaster) implements a concurrent PostgreSQL server on Linux GNU and macOS ARM64. It has its own runtime and data-directory contract; the embedded SDK endpoints do not switch to it. Check its release notes and README before integrating it.
