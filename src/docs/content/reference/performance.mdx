title: Measure performance
description: Measure startup, query latency, memory, and installed size for your own application.

Measure Oliphaunt with your schema, selected extensions, and target device.

## Separate the costs

| Measurement | Start and end points |
| --- | --- |
| First open | Before opening a new root → usable database handle |
| Reopen | Before opening existing persistent storage → usable handle |
| First query | Before submitting SQL → decoded result |
| Steady-state query | The same query after initialization, over repeated runs |
| Transaction | Before beginning → committed result |
| Backup | Before requesting backup → complete returned archive |
| App footprint | Installed application and resources, plus database storage |

Include storage initialization and extension activation when those happen during real startup. Measure packaged release builds; development builds and asset caches can change results.

## Measure a query

With an open native TypeScript database, record the elapsed time around the complete awaited operation:

```ts
const started = performance.now();
const result = await db.query('SELECT 42::int4 AS answer');
const elapsedMs = performance.now() - started;
console.log({ elapsedMs, answer: result.rows[0]?.answer });
```

Repeat measurements and report the median and a tail percentile alongside the sample count. Keep the device, runtime mode, schema, row count, SQL, parameter values, and extension selection constant when comparing runs.

## Investigate slow SQL

For an existing `notes(id, body)` table, use PostgreSQL's query planner with representative data:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, body FROM notes WHERE id = 42;
```

`ANALYZE` executes the statement. Use a disposable copy for statements with side effects. Check indexes, row estimates, result size, and time spent decoding before changing runtime settings.

Typed queries buffer results. Select only the columns you need and paginate large application reads. Batch related writes in bounded transactions instead of committing each row separately.

## Understand resource budgets

Treat a queue capacity, a read batch and an input limit as different settings. More queue space absorbs a burst and can increase waiting time. A larger read batch may reduce calls while retaining more scratch memory. A higher input limit accepts larger inputs; it does not speed up an already accepted query.

| Resource | Current behavior | Developer tradeoff |
| --- | --- | --- |
| Async operation admission | Omitting `admission` preserves the defaults: 64 pending operations in TypeScript, Swift and Kotlin; 256 queued commands in native Rust and 64 in WASIX Rust. Explicit settings include executing work | More waiting work retains more input without adding SQL execution parallelism. Ordinary Rust futures wait for capacity; TS/Swift/Kotlin reject full admission |
| Admitted input | These gates use a 128 MiB byte budget and permit a larger single input under their admission rules | This is a watermark for owned input, not a hard limit on total database or process memory. Explicit Swift settings reserve before structured packet encoding |
| Browser tool channels | Each channel has 256 KiB of usable capacity; a tool uses separate protocol and optional output channels | Full channels apply backpressure. Multiple channels and databases multiply the allocation |
| Read and callback batches | WASIX protocol callbacks deliver at most 64 KiB at a time | Large results can span many chunks. Chunk size does not limit total output or remove a single-message acceptance limit |
| OPFS helper I/O | Setup, snapshot reads and cleanup default to at most 16 concurrent operations per helper batch; `opfs(name, { maxConcurrentIO })` selects another positive count | Concurrency trades overlapping file work against storage contention. Changed-file publication retains its separate ordering |
| OPFS spare handles | Worker OPFS maintains 32 unused handles by default; `opfs(name, { spareFileCount })` accepts a non-negative count | More handles reduce overflow staging but increase startup and browser resource use. This reserve does not cap database file count |
| Desktop broker login | Each accepted SQL or management connection has five seconds to complete its handshake by default | A larger deadline allows slower login but retains unauthenticated connections longer. It ends after login and does not limit queries or backups |
| Guest memory | Embedded WASIX artifacts start with 128 MiB of linear memory, including an 8 MiB guest C stack | These are artifact settings. More guest stack reduces heap headroom within the same memory. The host engine's execution stack is separate |

Admission has the same explicit field meanings across the asynchronous SDKs. Omitting it retains each SDK's existing accounting. Transport, artifact and PostgreSQL settings have their own owners; these budgets do not establish a total process-memory bound.

Native TypeScript broker mode separately limits a collected SQL response to 128 MiB. Raw response streaming avoids that aggregate collection, but the broker's PostgreSQL reader still limits each backend message to its 128 MiB length-field policy. One large row can exceed a message limit even when the transport delivers small chunks. Streaming tool destinations also avoid complete stdout collection, while PostgreSQL and your destination retain their own memory costs.

## Tune the controls available today

Set both admission limits when you want to control bursts:

```ts
// Native TypeScript, WASIX TypeScript and React Native use the same open field.
const db = await Oliphaunt.open({
  admission: {
    maxPendingOperations: 16,
    highWaterMarkBytes: 32 * 1024 * 1024,
  },
});
```

| Field | Meaning | Raising it |
| --- | --- | --- |
| `maxPendingOperations` | Admitted preparation, queued and executing operations on one database; transaction handles share it | Accepts a larger burst and can increase queue delay; SQL still runs in order |
| `highWaterMarkBytes` | Conservative allowance for owned inputs and fixed transport allocations, retained until the owner finishes | Retains more waiting input; does not limit results or PostgreSQL memory |

A single operation above the watermark runs alone. While it owns the allowance,
zero-input operations also wait or reject. Rust futures wait fairly for capacity;
TypeScript, Swift and Kotlin reject full admission. Rust futures still waiting
for admission do not own a slot; their caller inputs are outside the allowance. Cancel, close and transaction
settlement retain their recovery path. BEGIN uses ordinary admission and releases
before the callback starts. The callback has a separate transaction lease, so a
limit of one is usable.
Known packet sizes and protected copies are reserved before allocation. JSON
inspection and custom encoders must produce a value before its encoded size is
known. Type inference or custom encoders can require an additional allowance
and reject final packet preparation; user code and result allocations are
outside the budget.

Supply the same two values through each language's existing configuration:

```rust
// Native oliphaunt or oliphaunt-wasix; asynchronous database builders only.
let db = AsyncOliphaunt::builder()
    .admission(AdmissionLimits::new(16, 32 * 1024 * 1024))
    .open().await?;
```

```swift
let configuration = OliphauntConfiguration(
    admission: .init(maxPendingOperations: 16, highWaterMarkBytes: 32 * 1024 * 1024)
)
```

```kotlin
val config = OliphauntConfig(
    admission = AdmissionLimits(maxPendingOperations = 16, highWaterMarkBytes = 32L * 1024 * 1024),
)
```

These fragments assume the imports from your [SDK quickstart](/docs/start).
Blocking Rust databases and endpoint-only server handles have no application
admission queue and do not accept this setting. WASIX Rust limits must fit its
owner semaphore; the JavaScript native actor validates the same range before open.

For browser OPFS, configure helper I/O on its storage constructor:

```ts
import { opfs } from '@oliphaunt/wasix-ts/storage/opfs';

const storage = opfs('main', {
  maxConcurrentIO: 4,
  spareFileCount: 32,
});
```

`maxConcurrentIO` defaults to 16. Lower values reduce overlapping asynchronous
setup, snapshot, restore and cleanup work. Higher values can reduce setup time
until storage contention dominates. This does not parallelize SQL.

`spareFileCount` defaults to 32 unused synchronous file handles in worker OPFS.
Higher values cost startup work and browser resources but reduce staging when a
query creates many files. Zero is allowed. The reserve does not limit the total
number of database files: overflow files are staged and saved in the recovery
journal before dependent changes can reach storage, then materialized at the
provider boundary. Large creation bursts can still use substantial staging
memory and extra storage I/O.

Worker OPFS reads and writes existing files directly. Placements without
synchronous access handles retain a complete working database in memory; the
concurrency setting does not bound that memory.

Use your SDK's PostgreSQL startup settings for database memory and SQL deadlines. Include units explicitly and inspect the effective values in the running database:

```sql
SELECT name, setting, unit, source
FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'wal_buffers', 'statement_timeout')
ORDER BY name;
```

| Setting | Purpose and tradeoff |
| --- | --- |
| `shared_buffers` | PostgreSQL data-page cache, selected at startup. A larger cache increases memory per instance |
| `work_mem` | Working memory for each sort or hash operation before spilling. Several operations within one query can multiply its use |
| `wal_buffers` | Buffers PostgreSQL WAL writes; independent of an SDK streaming queue |
| `statement_timeout` | Limits server statement execution. Time spent waiting in an SDK queue is a separate cost |

See PostgreSQL's [resource settings](https://www.postgresql.org/docs/18/runtime-config-resource.html) and [SQL timeout semantics](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-STATEMENT-TIMEOUT). Available workers and background maintenance depend on the runtime product; changing a PostgreSQL setting does not add unsupported workers to an embedded session.

The native C runtime also has process environment overrides: `OLIPHAUNT_STREAM_QUEUE_MAX_BYTES` selects the streaming queue capacity, normally 4 MiB, and is read when streaming starts; `OLIPHAUNT_STACK_BYTES` selects the backend thread stack, normally 8 MiB, before thread creation. Values must be complete positive decimal integers that fit the native size; invalid legacy overrides use the default. These are byte counts for native embedding hosts that can set the process environment. They are not per-database SDK options or WASIX settings. Raising PostgreSQL `max_stack_depth` does not allocate a larger thread or guest stack.

Compare one change at a time. Measure queue delay, query latency, bulk throughput, first-byte latency, and peak and retained memory. Include a slow destination and verify error recovery and close; throughput alone can hide excess buffering or slower cancellation.

## Configure broker login

Native TypeScript supplies per-connection controls in `broker` and process lifecycle deadlines in `timeouts`:

```ts
const db = await Oliphaunt.open({
  topology: 'broker',
  broker: {
    handshakeTimeoutMs: 10_000,
    recoveryTimeoutMs: 3_000,
    maxPendingHandshakes: 16,
  },
  timeouts: { startupTimeoutMs: 60_000, shutdownTimeoutMs: 5_000 },
});
```

Native Rust uses the same option on synchronous and asynchronous builders:

```rust
let mut db = Oliphaunt::builder()
    .broker()
    .broker_handshake_timeout(std::time::Duration::from_secs(10))
    .broker_recovery_timeout(std::time::Duration::from_secs(3))
    .broker_max_pending_handshakes(16)
    .startup_timeout(std::time::Duration::from_secs(60))
    .shutdown_timeout(std::time::Duration::from_secs(5))
    .open()?;
```

The default is five seconds per accepted connection. The deadline covers the
complete login, including partial reads and writes, rather than restarting when
another byte arrives. Valid values are 1 through 2147483647 whole milliseconds;
Rust durations round up to the next millisecond. Larger values allow slower
handshakes but keep unauthenticated connections longer.

This option requires desktop broker mode. It is separate from the SDK's wait
for the helper to start and PostgreSQL's `startupGUCs`. After login, it does not
apply to queries or backups, including slow backup destinations. Mobile brokers use the controls below. Custom desktop helpers must support
`--handshake-timeout-ms`, `--recovery-timeout-ms` and `--max-pending-handshakes`
when you select those overrides.

| Option | Default and meaning | Raising it |
| --- | --- | --- |
| `broker.recoveryTimeoutMs` / `.broker_recovery_timeout(Duration)` | 3 seconds to settle a disconnected stream before retiring the helper | Gives PostgreSQL longer to recover; delays forced cleanup |
| `broker.maxPendingHandshakes` / `.broker_max_pending_handshakes(count)` | 16 incomplete logins **per endpoint**. SQL and management have independent allowances; authenticated connections release their slot | Allows more simultaneous logins and retains more unauthenticated sockets |
| `timeouts.startupTimeoutMs` / `.startup_timeout(Duration)` | Helper launch through protocol readiness, after asset resolution. Native TS defaults to 60 seconds; Rust to 20 seconds | Allows slower startup and delays detection of a stalled helper |
| `timeouts.shutdownTimeoutMs` / `.shutdown_timeout(Duration)` | 5 seconds for owned teardown before forced process cleanup, after ordinary work drains | Gives shutdown longer to finish before escalation |

The two lifecycle settings also work on native server handles. Direct native
placement rejects them. Typed selections override the existing process
environment defaults. The native backend has a separate readiness wait, normally
60 seconds, selected by `OLIPHAUNT_STARTUP_TIMEOUT_MS`; a larger helper deadline
does not raise that inner wait. Pending-login counts must be positive and fit a `u32`.
New timeout values must fit the portable millisecond range above. Management
admission remains available when SQL logins are full; PostgreSQL cancellation
packets still enter through the SQL endpoint.

## Configure mobile broker cleanup

Swift and Kotlin keep lifecycle settings on their existing broker options:

```swift
import OliphauntBroker

let options = OliphauntBrokerOptions(
    startupTimeout: .seconds(30),
    operationTimeout: nil,
    recoveryTimeout: .seconds(3),
    shutdownTimeout: .seconds(3)
)
let db = try await OliphauntBroker.open(configuration: configuration, options: options)
```

```kotlin
import dev.oliphaunt.OliphauntBroker
import dev.oliphaunt.OliphauntBrokerOptions

val options = OliphauntBrokerOptions(
    startupTimeoutMillis = 30_000,
    operationTimeoutMillis = null,
    recoveryTimeoutMillis = 3_000,
    shutdownTimeoutMillis = 3_000,
)
val db = OliphauntBroker.open(context, config, options)
```

React Native forwards the same selections to the platform client and worker:

```ts
const db = await Oliphaunt.open({
  topology: 'broker',
  broker: {
    startupTimeoutMs: 30_000,
    recoveryTimeoutMs: 3_000,
    shutdownTimeoutMs: 3_000,
    // operationTimeoutMs: 60_000, // optional; includes queue time
  },
});
```

`recoveryTimeout` gives cancellation or a lost worker three seconds to produce a
known terminal result. `shutdownTimeout` gives destructive close three seconds
to retire the owner. Increasing either tolerates slower cleanup and delays
forced retirement. The client and worker receive the same settings, including
restore. These budgets do not impose an ordinary SQL deadline; the optional
operation timeout does. New cleanup values must be positive and fit
2147483647 milliseconds. Direct mobile placement rejects broker options.

## Configure WASIX startup and host resources

For a browser Worker database:

```ts
import { Oliphaunt } from '@oliphaunt/wasix-ts/worker';

const db = await Oliphaunt.open({
  timeouts: { startupTimeoutMs: 120_000, shutdownTimeoutMs: 120_000 },
});
```

Browser startup includes asset fetching, preparation, storage setup and protocol
readiness. Fetches receive cancellation signals. A shared preparation is cancelled
only after its last caller leaves. The browser default is 120 seconds.
`shutdownTimeoutMs` applies the Worker close deadline: it starts when `close()`
is requested, including accepted work still draining, and requests termination
on expiry. Increase it if you intentionally close during long operations.

The browser root placement accepts startup only. Without an isolated Worker,
a timer cannot interrupt synchronous Wasm or a blocked host callback. If an
owned allocation finishes late, cleanup keeps its storage lease until the
instance is closed. Use the Worker placement when you need guest termination.
Native-host WASIX placements, including `/worker`, reject lifecycle options:
addon owners need quiescent cleanup before their Worker realm is destroyed.
A JavaScript timer cannot establish that native code has stopped. Existing
native cleanup behavior is preserved.

For native-host WASIX databases and tools, configure the shared executor before
first use. This is process-wide, including Worker realms using the same addon:

```ts
import { configureHostRuntime } from '@oliphaunt/wasix-ts';

configureHostRuntime({
  asyncWorkerThreads: 2,
  maxBlockingThreads: 32,
  maxDedicatedThreads: 32,
  maxConcurrentIO: 4,
});
```

```rust
oliphaunt_wasix::configure_host_runtime(oliphaunt_wasix::HostRuntimeOptions {
    async_worker_threads: Some(2),
    max_blocking_threads: Some(32),
    max_dedicated_threads: Some(32),
    max_concurrent_io: Some(4),
})?;
```

| Option | Omitted default | Meaning and tradeoff |
| --- | --- | --- |
| `asyncWorkerThreads` | Tokio's CPU/environment selection (`TOKIO_WORKER_THREADS`) | Shared async executor workers. More threads can overlap host work, with more memory and scheduling cost |
| `maxBlockingThreads` | 512 | Ceiling for Tokio blocking workers, created on demand. A small ceiling can delay or starve file/host work |
| `maxDedicatedThreads` | `max(200, available CPUs × 100)` | Separate Wasmer pool for dedicated guest/host tasks. Workers are created on demand and retained. A small cap can starve nested guest work, including initialization |
| `maxConcurrentIO` | 4 | File helpers per initial-copy/publication operation. More I/O can reduce copying time until storage contention dominates; durability barriers remain mandatory |

All four accept positive counts fitting a `u32`. Databases and tools share the
Tokio executor and dedicated task pool. Omitted fields keep its selected values; a conflicting selection after
initialization fails. These are host controls, distinct from browser OPFS
`maxConcurrentIO`, PostgreSQL workers and artifact stack/memory settings.

WASIX `PgDumpOptions` and `PsqlOptions` accept `.startup_timeout(Duration)` in
Rust; WASIX npm tool options accept `startupTimeoutMs`. The budget ends when the
tool opens its virtual connection (first protocol activity in the browser).
It includes tool asset preparation and does not limit SQL execution or output
delivery afterward. Native WASIX defaults to 30 seconds; browser tools retain
no startup deadline unless selected. Expiry stops the owned guest/Worker and
waits for cleanup; blocking host work may delay that cleanup.

## Select physical archive limits

WASIX TypeScript physical backup and restore accept the same per-call policy:

```ts
const options = { archiveLimits: {
  maxArchiveBytes: 4 * 1024 ** 3,
  maxEntryBytes: 1024 ** 3,
  maxEntries: 131_072,
  maxPathBytes: 1024,
  maxPathDepth: 64,
} };
const archive = await db.backup(options);
await Oliphaunt.restore(destinationStorage, archive, options);
```

| Field | Browser default | What it accepts |
| --- | --- | --- |
| `maxArchiveBytes` | 2 GiB | Complete uncompressed TAR, including headers and padding |
| `maxEntryBytes` | 512 MiB | One file or metadata entry |
| `maxEntries` | 65,536 | All file, directory and TAR metadata entries |
| `maxPathBytes` | 1,024 | UTF-8 bytes of a normalized relative path |
| `maxPathDepth` | 64 | Relative path components |

Raising a ceiling permits larger archives; it does not reserve space or reduce
the memory needed to collect a complete backup. Every value is a positive safe
integer. Use the same selections when creating and restoring an archive. The
writer now rejects archives its matching reader would reject. Path safety,
duplicate-path checks and backup identity checks remain mandatory at every
setting. The physical writer retains its ustar field widths; larger path
ceilings cannot widen that format. Native-host WASIX keeps its existing
uncapped default; an explicit
`archiveLimits` selects the same policy (with omitted fields filled from the
table). Other native SDK backups do not acquire browser TAR limits.
These physical-backup settings do not change package/seed/ICU/extension import
ceilings.

## Compare runtime modes

Direct, broker, and server modes have different process and connection costs. Measure the mode you will ship. For async integrations, measure UI responsiveness or executor delay separately from SQL latency.

Browser persistence includes host-provider work. Compare memory and persistent storage only if you report that difference; an in-memory result does not predict durable write latency.

When comparing with SQLite, include installed size and memory as well as query speed. See [Moving from SQLite](/docs/learn/sqlite-upgrade) for the integration differences.
